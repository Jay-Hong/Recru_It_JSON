# 연속 목록 로딩 준비 확인

기준: `b7f7e8a`의 운영 코드와 `5f35030`의 진단 보강 브랜치.
속도 설정(클릭 1.6~2.8초, 스크롤 1.5~2.5초), 스크롤 횟수 54~58회,
급여 표본·상세 검증·텍스트 비교는 유지한다. 공고 수 810~870개는 종료 조건이 아니다.

## 확인한 동작과 한계

2026-09-15 작은 로컬 시험에서 22번째 스크롤의 목록이 315→345개로 늘면서
연속 요청이 발생했다. 345개 카드 모두 높이가 있었고 지역 텍스트가 비지 않았다.
위쪽으로 이동하자 진행 중인 응답 한 페이지가 마저 도착한 뒤 360개에서 안정됐다.
숨겨진 카드가 원인이라는 가설은 이 표본에서는 뒷받침되지 않았다.
이전 로컬 기록은 스크롤 21회, Actions 실패는 22회였다. 항상 같은 반복 번호라는
주장은 부정확하다. 사이트 변경 여부나 진단 코드와의 인과관계까지 확정한 것은 아니다.

## 보완 동작

- `observer.js:listState`는 진행 중인 XHR 개수, 사이트의 `loadFlag`, 누적 목록 요청 수를 나눠 기록한다.
- `observation.py:wait_list_bounded`는 요청 시작을 관측하면 첫 카드로 즉시 이동해
  목록 끝의 자동 로딩 표시에서 벗어난다. 연속 요청이 길어진 뒤에만 개입하는 방식이 아니다.
  페이지 데이터, 요청 본문, 콜백, 페이지 번호는 변경하지 않고 이미 시작한 응답은 끝까지 받는다.
- 진행 중인 요청·사이트 로딩 표시가 모두 꺼지고, 화면/모델 개수가 일치하며
  개수·이벤트·요청 수가 0.2초 동안 유지돼야 준비 완료다.
- 첫 스크롤에 한해 2.5초 동안 요청·증가가 없었던 기존 예외를 유지한다.
  그 이후 증가 없음은 목록 끝으로 간주하지 않는다. 목록 끝은 사이트의 명시적 완료 신호만 인정한다.
- `spiders/recru_it.py:scroll_list`는 진행 중인 요청이 있으면 다음 수동 스크롤을 보내지 않는다.
  계획 횟수 완료 또는 명시적 목록 끝에 도달한 뒤 최종 상태와 카드 표시 상태를 확인한다.
  숨겨진/크기가 없는 카드가 있으면 전체 목록을 정상 완료로 인정하지 않는다.
  빈 지역 글자는 별도로 집계하며, 이 숫자만으로 공고를 제외하거나 실행을 막지 않는다.
- `validate_run.py`는 새 최종 상태 기록이 없거나 불일치하면 반영을 차단한다.
  개별 공고의 기존 검증·재시도·경고 정책은 그대로다.

## 중단 상한

`settings.py`의 `optimizations.list_readiness`:

| 조건 | 상한 |
| --- | --- |
| 목록 개수/이벤트에 진전 없음 | 5초 |
| 스크롤 1회의 준비 확인 전체 | 10초 |
| 목록 수집 전체 | 240초 |
| 스크롤 1회 중 새 목록 요청 | 4회 |
| 목록 수집 중 새 목록 요청 전체 | 계획 스크롤 수 + 8회 |

상한은 **중단 기준**이다. 도달한 수집량을 정상 결과로 인정하지 않는다.
요청은 브라우저 안에서 비동기로 발생하므로 검사 시점 사이의 추가 요청까지 정확히 차단하는
서버 측 제한은 아니다. 전체 요청 여유 8회는 이전에 관측한 추가 4~6회에 여유를 둔
초기 운영값이며 서버의 허용량을 뜻하지 않는다. 429·503 중단도 유지한다.

## 시험

- 원래 연속 로딩과 위쪽 이동 효과를 확인한 작은 시험 1회.
- 보완한 실제 코드로 28회 스크롤: 420개, 수집 중 목록 요청 27회,
  최종 pending=false, 화면/모델 일치, 숨겨진 카드·빈 지역 텍스트 각각 0건.
- 로컬 HTTP/XHR 모의 브라우저 및 단위 시험으로 무한 성장, 무진전, 로딩 표시 잔류,
  요청/시간 상한, 첫 스크롤, 빈 목록 끝, 목록 감소, 숨김 상태의 반영 차단을 확인한다.
- 전체 Actions 시험은 시험 브랜치에서 1회 수행하고 결과·통계를 별도 보고한다.
  master 반영은 그 결과를 검토한 뒤 결정한다.

원시 측정은 저장소 밖 `Recru_It_JSON_measurements/list-settling/`에 보관한다.
