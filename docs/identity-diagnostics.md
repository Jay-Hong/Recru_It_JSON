# 식별 실패 진단 보강

첫 정기 실행 `34901460530`에서 경기 공고 하나가 재시도 후에도 `identity`로 확인되지 않았다.
두 상세 요청은 HTTP 200, 기록된 수신 크기는 각각 439바이트였다. 같은 크기만으로 삭제·마감,
서버 내부 오류 또는 빈 응답을 구분할 수 없어 응답과 화면 상태를 나눠 기록한다.

## 기록 항목

통계의 `identity_diagnostics_version=1`은 이 부가 기록을 지원한다는 뜻이다. 결과 JSON 형식은 같다.

- `attempts[].job_id`: 클릭 대상으로 준비한 목록 카드의 공고 ID.
- `attempts[].identity`: 시도 종료 시점의 상세 모델 상태. 기존 `identity` 검증과 같은 조건으로
  `missing`(모델 없음), `unchanged`(이전 객체 유지), `different_id`(다른 공고), `matches`를 구분한다.
  `model_present`, `model_replaced`, `model_job_id`도 함께 남긴다. 조회 실패는 `unavailable`이다.
  이 기록은 마지막 검증 호출보다 뒤에 읽으므로, 두 시점 사이에 화면이 바뀌었을 가능성은 남는다.
- `attempts[].detail_responses`: 해당 시도의 상세 요청만 담는다. 브라우저 요청 순번 `sequence`,
  CDP의 `request_id`, 요청에 사용된 `job_id`, HTTP 상태, `response` 진단이 있다.
  CDP 기록을 연결하지 못하면 `request_id=null`이며, 이미 수집한 브라우저 진단은 보존한다.
- `response`: `state`, 숫자 `rescode`와 `rescode_state`, `data_state`, 응답 데이터의 `job_id`.
  `data_state`는 필드 없음, null, 빈 객체/배열, 객체/배열 및 값의 자료형을 구분한다.
  ID나 코드가 예상된 숫자 형식이 아니면 원문 대신 null을 남긴다. 원래 사이트 판정에는 영향을 주지 않는다.

같은 공고를 재시도해도 응답은 요청을 시작할 때 붙인 시도 번호·요청 순번에 남는다.
현재 화면의 ID만 보고 이전 요청의 응답을 새 시도에 붙이지 않는다.

## 동작 범위와 한계

기존 XHR `loadend` 관측에서 상세 응답을 페이지 안에서 읽어 허용한 필드만 추린다.
응답 본문·연락처·본문 문구·오류 메시지는 진단 기록으로 보관하거나 WebDriver로 반환하지 않는다.
CDP 응답 본문 조회, 추가 사이트 요청, 요청 헤더/본문 변경은 없다. 목록 응답은 이 목적으로 읽지 않는다.
텍스트 응답은 262,144자를 넘으면 `too_large`로 남기고 JSON 파싱을 생략한다.
브라우저가 이미 JSON으로 변환한 응답은 전체를 복사하지 않고 필요한 필드만 읽는다.
빈 응답, JSON 파싱 불가, 지원하지 않는 응답 형식, 읽기 실패도 각각 상태로 남긴다.

요청 간격·스크롤 횟수·재시도·급여 표본·공고 검증·반영 기준은 유지한다.
`rescode`는 원인 구분을 위한 부가 정보이며 새 통과/중단 조건으로 쓰지 않는다.
응답 또는 모델 진단의 읽기 실패는 진단 누락으로 집계하고, 그 자체로 수집 성공·실패를 바꾸지 않는다.
단, 기존의 공고 확인 실패와 페이지 전체 관측 실패 처리는 그대로다.
필드 추출과 직렬화 비용은 추가되므로 실행 시간이 완전히 같다고 보장하지 않는다.

439바이트 기록만으로 과거 응답을 복원할 수는 없다. 이후 같은 공고가 반복 실패하는지와
응답 코드·데이터 형태를 비교할 수 있으며, 코드의 의미가 확인되지 않았다면 삭제·마감으로 단정하지 않는다.

## 검증

`tests/test_identity_diagnostics.py`는 외부 채용 사이트 대신 로컬 HTTP 서버와 실제 Chrome XHR을 쓴다.
정상 text/JSON 응답, 내부 오류, 누락/빈 데이터, 이전 모델 유지, 다른 ID, 같은 공고 재시도,
CDP 연결 누락, 잘못된 JSON, 큰 응답, 진단 읽기 예외, 허용하지 않은 식별자/문자열을 확인한다.
앱이 받은 응답과 요청 횟수/본문이 유지되고, 진단에 본문이나 오류 메시지가 남지 않는지도 확인한다.
기존 검증기를 사용해 새 진단의 누락만으로 반영 정책이 달라지지 않는 것을 확인한다.

실제 전체 수집 시험과 master 반영 상태는 별도로 확인한다. 시험 결과 JSON을 master로 가져오지 않는다.
